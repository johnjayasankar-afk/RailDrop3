# Accessibility

Audited 2026-09-27 against the running app at 1440×900 and 390×844, light and
dark. Every claim below is something a test asserts on the rendered page —
`tests/e2e/accessibility.spec.ts` — not something read off the source.

**What this is not.** It is not a substitute for using the product with a screen
reader, and nobody has. The checks here are the mechanical failures that are
invisible in review and immediately obvious to someone who cannot use a mouse.
They are the subset of what axe-core checks that has ever caught anything in
this codebase, hand-rolled because axe is a runtime dependency for a page of DOM
queries and the brief asks before adding one.

## What is checked, and why each one matters

| Rule                                     | Why it is not cosmetic                                                                                                                        |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Every control has an accessible name     | A nameless button is announced as "button". There is no way to find out what it does.                                                         |
| Heading levels never skip                | The outline is how people navigate a long page. h2 → h4 puts a hole in it.                                                                    |
| One `main` landmark, exactly one `h1`    | "Skip to main" and landmark navigation both depend on there being one of each.                                                                |
| No positive `tabindex`                   | It jumps that element to the front of the tab order for the whole document, reordering everything else relative to it.                        |
| Focus is visible at every stop           | `outline: none` with nothing in its place is the commonest way to make a page unusable by keyboard while looking fine.                        |
| The skip link exists and its target does | It is the first thing a keyboard user meets, and useless if `#main` is not there.                                                             |
| The command palette is a real dialog     | `role=dialog`, focus on open, `aria-activedescendant` on the input, and Escape gets you out. A dialog you cannot leave by keyboard is a trap. |

Run on the landing page, `/how-it-works`, `/watches/new`, `/dashboard`, and a
live watch board — the densest page in the app and the one where a nameless icon
button is most likely to slip in.

## Result

**36 checks pass across both viewports. Nothing was found to fix.** That is worth
stating plainly rather than dressing up: the app was already in good shape on
these rules, and the value of the audit is that it is now a test rather than an
afterthought.

The one failure during the audit was in the test, not the app: `getByRole
("combobox")` matched the board's Sort `<select>` as well as the palette's input,
because `<select>` carries an implicit combobox role.

## Contrast

Measured in the browser with a compositing walk up the ancestor chain, so a
translucent surface is scored against what is actually behind it rather than
against its own `rgba`.

| Surface                      | Ratio    |
| ---------------------------- | -------- |
| Body text, dark board        | 17.3 : 1 |
| Command palette key badges   | 11.7 : 1 |
| Palette group headings       | 10.6 : 1 |
| Disabled-command explanation | 7.7 : 1  |
| Muted text on the dark board | 7.2 : 1  |
| Coverage tag (light)         | 6.5 : 1  |

The lowest pair in the app is 6.5 : 1, against a 4.5 : 1 requirement for body
text. Two of these were failures found by measuring rather than looking: the
coverage tag was 1.67 : 1 when a re-themed `--drop` was paired with a fixed amber
background, and the palette's key badges were about 1.4 : 1 when mint text
inherited the global `kbd` rule's white fill. Both are in the light-and-dark
suite now.

## Motion

Everything that animates is inside a `prefers-reduced-motion: reduce` block that
sets `animation: none`: the split-flap ticks, the board toast, the fuse bars, the
command palette, the empty-board flaps. The reduced-motion path is a static
state, never a missing one — nothing is conveyed by movement alone.

## Known gaps

Stated rather than left for someone to discover.

- **No screen-reader testing.** Not VoiceOver, not NVDA, not JAWS. The
  structural rules above are necessary and nowhere near sufficient, and the
  places most likely to be wrong are the ones that are hardest to check
  mechanically: whether the board's live regions announce a recheck usefully,
  and whether the split-flap price transitions are read as one value changing or
  as a stream of characters.
- **The board is a `div` grid, not a `table`.** It has table semantics in the
  design and none in the markup, so a screen reader cannot be told "column 3,
  row 7". This is the largest known gap.
- **No keyboard-only walkthrough of the whole task.** Tab-order visibility is
  tested; whether the order is _sensible_ on the board is not.
- **Colour is load-bearing in one place**: save-green versus drop-amber on the
  fare figures. Both are also stated in words next to the figure, so nothing is
  colour-only, but the fast read is colour.
